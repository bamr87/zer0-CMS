# Recorded site builds (PLAN P1)

Each `<site>/manifest.json` records what one site's Jekyll build wrote, made on 2026-10-22 while every site still built with Jekyll. A site keeps its URLs, content, feeds and redirects whichever way it renders ([ADR 0006](../../../docs/adr/0006-one-python-platform.md) decision 4), so it moves — to the Jekyll-theme option ([PLAN](../../../docs/plan/PLAN.md) P2) or to the React renderer (P6, P7) — only when its new build reproduces its recording. These files are that baseline: never edit one by hand, and re-record one only with `tools/site_manifest.py`.

## What a recording holds

[`tools/site_manifest.py`](../../../tools/site_manifest.py) writes them (schema `site-manifest/v2`, stdlib Python, tests in [`tools/tests/test_site_manifest.py`](../../../tools/tests/test_site_manifest.py)) as JSON with sorted keys and a trailing newline:

- `paths` — every output file and its media type. An HTML page also has its `title`, its `text` and `text_sha256`, the SHA-256 of the text's blocks joined with spaces.
- `feeds` — each Atom or RSS file's entries (`id`, `link`, `title`, and `published` and `updated` as UTC instants, however the feed spells them), in the feed's order.
- `sitemaps` — each sitemap's URLs, sorted.
- `redirects` — each page that redirects with a meta refresh (as jekyll-redirect-from writes them) and its target. No recorded site has one today.
- `built_with` — what the build resolved that the repository does not pin: every gem in the bundle's `Gemfile.lock` with its version (the platform suffix dropped), and the commit the site's `remote_theme:` pointed at. A comparison prints what changed here, as notes beside the differences, and does not count it.

**A page's text is its own content, not the theme's layout around it.** It is the text of the elements the page marks as its entry's content (microformats `e-content`, schema.org `itemprop="articleBody"` — the theme's posts and notes), else of the theme's content column (`bd-content`, where the theme writes every other page's Markdown), else of its `<main>`, its `<article>`s, its `<body>`. Inside that, the `header`, `nav`, `footer`, `aside`, `button`, `svg`, `time`, `script`, `style`, `noscript` and `template` elements are left out, each block element starts a new block, and whitespace is collapsed. So the title banner (the author, the dates, "Estimated reading time", "View source"), the share and "Edit on GitHub" menus, the table of contents and the sidebars — everything the theme writes around the content — are not part of a recording, and a renderer that lays the page out its own way reproduces the recording by writing the same words. A column keeps what the theme writes in it beside the Markdown, such as the backlinks of zer0-pages's Obsidian docs pages; on a post or note the entry's content alone counts. A page with neither (each site's home page, drsai's book pages, parodynews's layout-less posts) keeps the text of its whole `<main>`, or of the whole page when it has none. The words are stored, not only their digest, so a difference shows which blocks changed, and a finer rule can be applied later without a Jekyll build.

**Dates.** A feed entry's dates come from its post, so they are recorded; the feed's own `<updated>` is the build's clock and is not. A sitemap's `lastmod` is not recorded either: for a page with no date of its own it is the build's clock (all 14 of drsai's, 107 of zer0-pages's 153, 5 of the cookbook demo's 8, 7 of irony-works's 57). Nor are the dates on a page: a page with no date shows the build's date as its published date (108 zer0-pages pages, 7 of irony-works's, each demo's about page), and the theme prints its dates in the title banner. A post's date is held by its feed entry and, where its permalink has one, by its URL.

**Other files.** The bytes of styles, scripts, images and fonts are not recorded, only their paths and types. Most are the theme's — zer0-pages-remote, one page of its own, writes 340 other files, 337 of them the theme's `assets/` — which a renderer in another design system does not reproduce, so `compare --pages` (and `--check --pages`) leaves every path that is not an HTML page out of the comparison; the full comparison, which the Jekyll-theme option is measured with, keeps them. Media types come from a fixed table in the tool rather than Python's `mimetypes`, whose table changes between releases, so the same build gives the same bytes under Python 3.12, 3.13 and 3.14 alike.

## How they were built

**The routed sites**, the way `.github/workflows/pages.yml` builds each one, in a `ruby:3.3` container: the routes from `bin/zer0 routes --json`; per site, a config file that sets only `url: "https://bamr87.github.io"` and `baseurl: "/zer0-CMS<route>"` (the workflow's defaults for `vars.PAGES_URL` and `PAGES_BASE_PATH`), `PAGES_REPO_NWO=bamr87/zer0-CMS`, `LANG=C.UTF-8` and `TZ=UTC`; `bundle install` in the site's bundle directory; then `bin/zer0 run pages <site>`, the site's own `pages` task (`bundle exec jekyll build --config "_config.yml,$ZER0_PAGES_CONFIG" --destination "$ZER0_PAGES_DEST"`). `--check` and `--write` run exactly that wherever they run:

- **In UTC.** Jekyll reads a post's date in the process's time zone, and a date permalink is that local date: parodynews's `_posts/2025-05-02-injustices.md` (`date: 2025-05-02T00:01:30.311Z`) is `posts/2025/05/02/injustices/` in UTC but `posts/2025/05/01/injustices/` in America/Denver. pages.yml's runners are UTC (the workflow sets `TZ: UTC` to say so), and so is every recording.
- **Without the caller's build variables.** No `JEKYLL_*`, `PAGES_*`, `ZER0_*`, `OCTOKIT_*` or `BUNDLE_GEMFILE` variable reaches the build except the ones the tool sets: pages.yml's runners have none of them, and each changes a build — `JEKYLL_ENV=development` switches on the theme's development-only blocks, drsai's Gemfile swaps in a local theme checkout when `ZER0_THEME_LOCAL` is set, a token changes what jekyll-github-metadata fetches, `BUNDLE_GEMFILE` loads another bundle.
- **Leaving no lockfile.** A `Gemfile.lock` the bundle writes where none is committed is removed after the build, so the next local run resolves afresh, as CI does. Jekyll's caches stay, as after any local build.

**What floats.** Neither the gems nor the theme are pinned for five of the seven routed sites: zer0-demo-cookbook, zer0-demo-garden, drsai, wargames and zer0-pages-remote commit no `Gemfile.lock` (the fleet's always-latest policy), and every remote-theme site fetches the theme's default branch at build time. A gem release (jekyll-seo-tag changes titles, jekyll-feed entries, kramdown or rouge the text) or a theme commit can therefore change a recording with no change in this repository. `built_with` records what each recording resolved — for these, the gems of 2026-10-22 (jekyll-feed 0.18.0, jekyll-seo-tag 2.9.1 and jekyll-remote-theme 0.6.2 for the Jekyll 4 sites; github-pages 232 and zer0-image-generator 0.9.0 for drsai; github-pages 231, the newest its `< 232` allows, for zer0-pages-remote) and the theme at `98e978d` — and `--check` and `compare` print every version that resolved differently below the differences. zer0-pages and parodynews commit their lockfiles; zer0-pages takes the theme gem (1.28.0) from its own. P2's option pins the theme by tag.

**The two sites nothing routes yet**, the way this repository builds them today:

- `2005` — the way `sites.yml` builds it: its own `build` task (`bundle install`, then `bundle exec jekyll build` with its own `_config.yml`, whose `url` and `baseurl` are `https://year-of-ai.github.io` and `/2005`, where year-of-ai.github.io publishes it), on a copy of the tree, in `ruby:3.3`, with `TZ=UTC`, `LANG=C.UTF-8` and `PAGES_REPO_NWO=bamr87/zer0-CMS`.
- `irony-works` — the way `irony-works.yml` and bamr87/irony-works's own publish workflow build it: on a copy of the tree, Node 22 runs `npm i js-yaml --no-save`, `engine/scripts/preview.mjs` and `engine/scripts/transplant.mjs`; then GitHub Pages' own builder — `actions/jekyll-build-pages@v1`, which is the image `ghcr.io/actions/jekyll-build-pages:v1.0.13` (github-pages 232, Jekyll 3.10.0, Ruby 3.3.4) — builds it with its own `_config.yml` (`https://bamr87.github.io`, `/irony-works`), the action's defaults (`JEKYLL_ENV=production`, set by the builder) and `GITHUB_REPOSITORY=bamr87/irony-works`, the repository that deploys it. The builder's gems are its image's, so its `built_with` names only the theme.

Since P2 `--check` rebuilds these two as well, through their `build` tasks (below); before it, they were re-recorded by hand with the same steps and `python3 tools/site_manifest.py build <its _site> --site <name> --source <the built copy> --out web/site/fixtures/<name>/manifest.json`. `sites/1987` has no Jekyll configuration and no build, so there is nothing to record; its first build, once it has one, is its recording.

## The Jekyll-theme option (PLAN P2)

Eight of the nine recorded sites now build with the Jekyll-theme option ([`tools/jekyll_theme.py`](../../../tools/jekyll_theme.py), [ADR 0006](../../../docs/adr/0006-one-python-platform.md) decision 4) and reproduce their recordings exactly — the full comparison, the theme's asset files included — with no Ruby file left in their trees. Each site's `render:` setting in the root `workspace.yml` names the theme's tag and the Jekyll server; the option exports the files git tracks with the route's `url`/`baseurl` and `remote_theme: bamr87/zer0-mistakes@<tag>` merged into `_config.yml`, runs the site's `before:` step on that copy, and builds it in Docker.

**The theme is pinned at `v1.31.3`**, the tag on `98e978d21f2d…`, the commit the theme's `main` was at when every remote-theme recording was made — so the pin changes nothing a recording holds, and a later theme release reaches a site only when its tag moves, with the site re-recorded and the reason said. `built_with` records the pin and the commit it resolved to, and the server's image; a comparison with a P1 recording therefore prints the theme's key changing from `bamr87/zer0-mistakes` to `bamr87/zer0-mistakes@v1.31.3` at the same commit, which is a note, not a difference.

**Two servers, because the recordings were made by two Jekylls.** GitHub Pages' own builder (`github-pages`: the image `ghcr.io/actions/jekyll-build-pages:v1.0.13` that `actions/jekyll-build-pages` runs, github-pages 232, Jekyll 3.10.0, run through its own entrypoint) reproduces every site recorded with the github-pages gem — drsai, 2005 and irony-works (232) and parodynews and zer0-pages-remote (231, Jekyll 3.9.5: no recorded fact differs) — and every plugin those sites list is on its allow-list. It cannot reproduce the sites recorded with Jekyll 4.4.1: it always adds GitHub Pages' default plugins (titles from headings, optional front matter, relative links, a README as the index), defaults `future: true`, replaces Jekyll's default excludes instead of adding to them, and runs Jekyll 3.10's kramdown, jekyll-feed 0.17 and jekyll-seo-tag 2.8 — so `jekyll-4`, an image built from [`tools/jekyll/Dockerfile`](../../../tools/jekyll/Dockerfile) with Jekyll 4.4.1 and exactly the gems those recordings' `built_with` lists, on the recordings' Ruby (3.3.12), builds the installer demos and wargames. Both run with `JEKYLL_ENV=production`, as GitHub Pages does; the routed recordings were made with Jekyll's default, development, and no recorded fact differs between the two.

**zer0-pages does not move yet.** Built through the option — the theme at `v1.28.0` (`227fed10`, the tag of the gem 1.28.0 its `Gemfile.lock` holds), the jekyll-4 server, and its Obsidian bridge resolved in Python before the build ([`tools/obsidian/`](../../../tools/obsidian/__init__.py)) — it reproduces all 203 pages at their paths with their titles, its feed and sitemap, and the text of every page but five; every Dataview table, wikilink and callout comes out as the plugins wrote it. Two differences remain, and both come from the option itself, not from the port:

- **88 extra files** (`extra    assets/…` in the full comparison, none in `--pages`): the theme's own images that the gem leaves out of its package — the 18 `assets/backgrounds/{gradients,patterns}/*.svg`, 47 `assets/images/previews/*.png`, 17 `assets/images/quickstart/*.png`, and `assets/images/{gravatar.png,zer0-checkpoint-1.png,zer0-checkpoint-2.png,zer0-mistakes-wizard.png,authors/vega.svg,notebooks/test-notebook_files/test-notebook_4_0.png}`. `remote_theme` copies the theme repository's whole `assets/`, and Jekyll's `exclude:` does not reach a theme's assets.
- **More backlinks on five pages** (`text` of `docs/obsidian/{index,getting-started,authoring-workflow,syntax-reference,troubleshooting}/index.html`): the theme's "Linked mentions" panel scans every other page's content for a link to this one. Inside the plugin build a page's wikilinks were rewritten only when that page was rendered, so a panel saw the links of the pages Jekyll had rendered before it and missed the rest — the plugin's own comment calls that order-dependent. Resolved before the build, every page's links are visible to every panel: authoring-workflow gains a panel with 5 mentions, getting-started goes from 1 to 6, index from 9 to 14, syntax-reference from 5 to 8, troubleshooting from 4 to 6.

Neither can be reproduced without changing the site or the option, so zer0-pages keeps its Gemfile, `Gemfile.lock`, `pages/_plugins/` and Ruby tests and builds as before; moving it is one commit — its `render:` setting (`{as: jekyll-theme, theme: v1.28.0, server: jekyll-4, obsidian: true}`), its `pages` and `build` tasks on `tools/jekyll_theme.py`, the Ruby files and `docker-compose.yml` deleted, and its recording re-made from the option's build with these two differences as the stated reason — once the owner accepts them.

## Rebuild and compare

```bash
python3 tools/site_manifest.py --check                  # rebuild every routed site as pages.yml does, compare each with its recording; exit 1 on any difference
python3 tools/site_manifest.py --check --site drsai     # one site
python3 tools/site_manifest.py --write --site drsai     # re-record it, and say why in the commit
python3 tools/site_manifest.py build <dir> --site <name> --out <file> [--source <dir>]   # the manifest of any built tree (the renderer's, in P6)
python3 tools/site_manifest.py compare [--pages] <recorded> <candidate>                 # what differs; exit 1 when anything does
```

`--check` and `--write` need what `pages.yml` needs: for a site on the Jekyll-theme option, Docker and Python with PyYAML (the option runs its Jekyll server in a container; `--check` also rebuilds 2005 and irony-works, through their `build` tasks with their own config, as recorded); for zer0-pages, still on its Gemfile, Ruby 3.3 with bundler — run that one in a `ruby:3.3` container that mounts the repository at its own path: `docker run --rm -v "$PWD:$PWD" -w "$PWD" ruby:3.3 python3 tools/site_manifest.py --check --site zer0-pages`. Both need the network (the server's image or the gems, the theme).

**In CI, `pages.yml` does the comparison on every run** — on every pull request and push that touches a site, `workspace.yml`, the workspace tool, the option, the tool or a recording: after each routed site's build it records what the build wrote (`build --built-with` for a site on the Jekyll-theme option, `build --source <its bundle directory>` for zer0-pages) and compares it with the recording here; `sites.yml` does the same for `2005` and `irony-works.yml` for `irony-works`. A difference is listed in the job summary with the blocks of text that changed and the versions that resolved differently, and the fresh recording is uploaded as the `site-manifest-<site>` artifact: when the change is intended, unzip it over this directory and commit it with the reason. **On a pull request a difference fails the build of every site on the Jekyll-theme option** — every input of those builds is pinned (the theme's tag, the server's image, irony-works's npm packages), so a difference is a change to the site, the setting or the option, and the pull request that makes it re-records it. zer0-pages, still on its Gemfile, only warns; a push to `main` only warns in `pages.yml`, so a difference never stands between a site and its deploy; dispatching pages.yml with `check: true` fails on any difference. Nothing commits a recording on its own: a baseline a machine rewrites is no baseline.

A recording describes the build as it was. When a site's content changes on purpose (a new post), re-record that site in the same commit; when it changes by accident, pages.yml's warning is what notices.

**Determinism.** Every recording was made twice, and the two are byte-identical. The seven routed sites were recorded through the tool in a `ruby:3.3` container, in place, and then again through `--write` from a copy of the tree on the container's own filesystem (another directory order), with a fresh gem install and a caller environment that changes each build if it leaks into it — `TZ=America/Denver`, `JEKYLL_ENV=development`, `PAGES_ENV=dotcom`, and `ZER0_THEME_LOCAL` and `BUNDLE_GEMFILE` pointing nowhere. `2005` and `irony-works` were built twice by their recipes, `2005` the second time with a fresh gem install. Every build tree gives byte-identical recordings under Python 3.12, 3.13 and 3.14. Then `--check` itself — the final tool, a fresh copy of the tree, the same hostile environment — rebuilt the seven routed sites and found each `identical`, with no gem or theme resolved differently.

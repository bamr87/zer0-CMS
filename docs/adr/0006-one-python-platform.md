# ADR 0006 — One Python platform with a React frontend: a complete, modern, AI-assisted CMS that manages, monitors and improves sites; every merged repository absorbed with its content and capabilities; no Ruby

- **Status:** accepted 2026-10-21; implemented in [`../plan/PLAN.md`](../plan/PLAN.md) Phase P, with Phase G's absorptions re-pointed at it. The target is described in [`../plan/TARGET.md`](../plan/TARGET.md); every capability, and where it comes from, is in [`../plan/capabilities.yml`](../plan/capabilities.yml). The pull request that adds this file lands P0 (this record, the target, the ledger, and the gate that enforces them).
- **Amends:** [ADR 0004](0004-one-platform.md) — decision 1's carve-out ("Jekyll — the theme and the image-generator gem — stays Ruby") is withdrawn, and so is G11's "the stdlib `bin/zer0` workspace tool stays"; decision 2 ("the Wagtail admin is the CMS … no new SPA is started") is replaced by decision 2 below; decision 3 (the extension as client) is strengthened by decision 9 below; decision 8 (agent definitions are GitOps) stands for tool-using agents and is complemented by user-managed assistants (decision 7); the retire table's "the gem keeps shipping" is replaced by decision 11. Every other decision of ADR 0004 (one backend, OIDC, enterprise rows, cloud-agnostic deploy, parity gates before deletion) stands. [ADR 0005](0005-theme-goes-home.md) — decisions 1 and 2 stand (the theme and its studio live in `bamr87/zer0-mistakes`, and that repository's Ruby is that repository's business); decisions 3 and 4 (each site pins the theme, drsai builds against the theme's `main`) are superseded for the sites in this repository by decision 4 below; decision 5 stands as an import fixture.
- **Inputs:** the owner's direction of 2026-10-21, given after an agent session read a stale `main` and harmonized the theme's docs inside this repository (#55), in their words: "this repo needs to be cleaned up, normalized, refactored into a single platform while retaining the functionality. all of the barodybroject/parodynews capabilities need to exist. there shouldn't be any ruby code" · "the frontend should use react, and designed to manage/review/create content" · "all the repos that were merged need to be refactored or absorbed. the goal is to keep the content, features, and capabilities" · "perform a complete rewrite if necessary. the vscode extension should be aligned with the capabilities with the frontend. there should be AI adapters/integrations that help with the creation/development of content such as the model built in barodybroject. rewrite/refactor these models and views to be scalable and manageable" · "incorporate all the capabilities of modern CMS tools and frameworks. use existing libraries where possible. this should also have the capability to manage, monitor, and evolve/improve sites. the AIEO tool and functionality should also be incorporated" — and three answers the same day: React renders the public sites too; Wagtail stays as a headless library; the VS Code extension stays, as a client.

## Context

The repository was assembled by importing fifteen repositories with their history (ADR 0002). ADR 0004 then chose one backend but kept three exceptions that left two languages on the server side — Jekyll (and with it the sites' Gemfiles and plugins), the image-generator gem with its byte-identical Ruby port, and the Ruby `bin/zer0` — plus the Rails fleet CMS until each of its functions is absorbed. It chose the stock Wagtail admin as the only CMS UI, although two of the absorbed apps (aieo, parodynews) already had React frontends, and it described the absorptions as ports.

Agents kept misreading the target. The direction lived in five ADRs that amend each other; the always-loaded AGENTS.md described today's code at the same weight as the destination; the plan's own rule ("pick the first unchecked milestone") pointed at milestones the later ADRs had overtaken; and one stacked pull request (#52) merged into a branch instead of `main`, so `main` contradicted the owner for a day — long enough for automated fleet passes to do careful work in the wrong place. A target that has to be reconstructed from five documents will be reconstructed wrongly. This record states the whole target once, [`TARGET.md`](../plan/TARGET.md) describes it, the ledger makes "nothing is lost" checkable, and a gate fails the build when the work moves the wrong way.

## The target, in one paragraph

**One Python platform** (`content/`: Django, with Wagtail as a headless content library, Celery, Postgres + pgvector) is the system of record and the only backend. **One React codebase** (`web/`) is the only web frontend: the **studio**, where people *manage*, *review* and *create* content and operate their sites, and the **site renderer**, which turns each site's content into its static public site. **The VS Code extension** (`src/`) is a client with the studio's capabilities, through the same API. The platform has the capabilities of a modern CMS, built on established libraries rather than hand-rolled; an **AI content layer** — provider adapters, assistants, pipelines, output schemas, briefs and conversations, rebuilt from barodybroject's model to scale — helps create and develop content; and the platform **manages, monitors and improves sites** in a loop whose signals include AIEO's citability scoring. **Every repository that was merged in** is absorbed with its **content, features and capabilities** intact, tracked one capability at a time. **No Ruby** remains.

## Decisions

| # | Decision | Mechanism that enforces it |
|---|---|---|
| 1 | **No Ruby in this repository.** Every `.rb`, `.rake`, `.ru`, `.erb`, `.gemspec`, `Gemfile`, `Gemfile.lock`, `Rakefile` and `.ruby-version` goes, every Ruby executable (`bin/zer0`, `rails/bin/*`) is replaced by a Python one, and no workflow installs Ruby. Until then the existing Ruby is a **ratchet**: a per-directory ceiling that only goes down, and no new directory may start holding Ruby. Files that merely *model* an outside Jekyll site for a test (a two-line `Gemfile` fixture) are listed as fixtures, not code. | `tools/check_absorption.py` (`ruby_ratchet:` and `ruby_fixtures:` in [`../plan/capabilities.yml`](../plan/capabilities.yml)), run by `zer0-workspace.yml` on every pull request |
| 2 | **React is the frontend.** `web/` is one React + TypeScript + Vite codebase. Its **studio** is designed around three jobs — *manage* (sites, page trees, media, settings, people, assistants, agents, jobs), *review* (suggestions with diffs, revisions, workflow tasks, comments, agent runs, scores, monitor findings) and *create* (pages, drafts, briefs and conversations, with or without AI) — and every absorbed app's screens move into it. It talks to the platform only through the platform's APIs, through a client generated from the committed schemas. The Wagtail admin stays as an operator fallback until the studio covers it, then is closed to editors. The aieo and parodynews React code is source material, not a second app. | PLAN P2; `web/` unit tests and the verify kit's studio scenarios; the generated client's drift check against `schemas/` |
| 3 | **Wagtail is a headless library.** Its page tree, revisions, workflows, locking, comments, StreamField, images, documents, forms, redirects, search, settings, snippets and locales are the data layer; nothing new is built as a Wagtail admin view. | review rule in `AGENTS.md`; PLAN G2 superseded by P2 |
| 4 | **React renders the public sites.** The site renderer pre-renders each site to static HTML (pages, feeds, sitemap, robots, search index, redirects) and deploys it. It reads the site's **source tree as the platform exports it** — Markdown, front matter, data files and config, the shape `export_jekyll` writes byte for byte — so it builds in CI with no live database, for a site still on files and for a DB-first site alike; Liquid in content is evaluated by a JavaScript Liquid engine. It must keep each site's **URLs, content, feeds and redirects**: before a site leaves Jekyll, its Jekyll build is recorded as a parity fixture (every URL and a normalized text digest per page), and the site switches only when the renderer reproduces it. Site features built as Jekyll plugins (zer0-pages's Obsidian bridge: wikilinks, embeds, callouts, Dataview, the graph index) are rebuilt as renderer plugins. The zer0 design is ported into React components at a recorded tag of the theme; the theme itself stays in `bamr87/zer0-mistakes`. | PLAN P1 (fixtures, recorded while Jekyll still runs) and P5 per site; the fixture and its test under `web/site/` |
| 5 | **A modern CMS, built on established libraries.** The platform's capability catalog ([`TARGET.md`](../plan/TARGET.md) § Capabilities, machine-readable in the ledger's `platform:` section) covers what current CMS tools offer — structured content types, a block editor, live preview, revisions with diff and revert, editorial workflows with assignments, scheduling, comments and locking, localization, taxonomy, full-text and semantic search, redirects, forms, reusable snippets and navigation, a media library with focal points and renditions, roles and per-site permissions, audit log, webhooks and events, REST/GraphQL/MCP APIs, multi-site, bulk import/export — and each is built on the library that already does it (Wagtail, django-allauth, DRF, drf-spectacular, django-filter, Celery, pgvector, jsonschema, the provider SDKs; TanStack Query/Router, a component library, a block editor in `web/`). Hand-rolling a capability a maintained library provides needs a reason in the pull request. | review rule; `TARGET.md` § Libraries names the chosen library per capability |
| 6 | **A rewrite, where a port would not scale.** The merged repositories' code is source material. What must survive is their *content* (imported) and their *capabilities* (ledger rows); their models, views and services are rebuilt to the platform's rules — a service layer with thin views, async jobs for anything that calls a model or the network, owner/site scoping in one place, public ids rather than prefixed string keys, per-site settings rather than singleton rows, encrypted credentials, typed and paginated APIs. Every redesign records its old → new mapping in the ledger, and an importer moves the data. | the ledger (each source capability names its platform `target`); each source's importer and its round-trip test |
| 7 | **An AI content layer, rebuilt from barodybroject's model.** Provider **adapters** behind one registry (`claude_code`, `anthropic`, `openai`, a LiteLLM catch-all, `recorded` and `fake` for tests) with per-provider configuration, health checks and a synced model catalog; user-managed **assistants** (persona, instructions, model, parameters, output schema) that may only *propose*; ordered **pipelines** of assistants; an **output-schema** library (barodybroject's bundled article, news and content-detail schemas seeded); **briefs** that turn a prompt into a structured draft; and **conversations** (threads and messages, replayed to any provider, promotable to a brief or a draft). Every generation runs as an `AgentRun` on Celery, streams to the client, and is costed and budgeted. Tool-using **agents** stay GitOps and eval-gated (ADR 0004 decision 8); assistants are the user-editable layer above them. There is one LLM client — the adapter registry — and nothing calls a provider SDK outside it. | PLAN G8; `content/tests/ai/`; the registry test that no module outside `content/ai/providers/` imports a provider SDK |
| 8 | **The platform manages, monitors and improves sites.** *Manage*: a site registry with per-site settings, design and domains; sync, render and deploy as jobs with logs. *Monitor*: scheduled checks with history and alerts — uptime, broken links, performance and Core Web Vitals, accessibility, SEO, the doctor's consistency checks, analytics (GA4, Search Console, DataForSEO), and **AIEO** citability scores. *Improve*: an evolution loop in which agents read those signals and the site's editorial plan and propose improvements — refreshes, fixes, internal links, new topics, rewrites for citability — as suggestions a person accepts, then measures the result. | PLAN G4 (manage), G12 (monitor), G7 (AIEO), G13 (improve); each app's tests |
| 9 | **The extension has the studio's capabilities.** The VS Code extension is a client of the same API and implements every studio capability that belongs in an editor — create, edit, preview, revisions, review of suggestions, assistants, pipelines and conversations, briefs, AIEO scores and monitor findings for the open page, distribution — plus its file mode for sites still on files. Parity is tracked per capability and surface in the ledger, and a capability added to one surface without the other is a reported gap. | the ledger's `platform:` surfaces (`studio`, `extension`, `api`, `mcp`), reported by `tools/check_absorption.py --report`; PLAN G10 |
| 10 | **Every merged repository is absorbed with its content, features and capabilities.** Each source is listed in the ledger with every capability it has, its platform `target`, its status (`missing`, `partial`, `done`, or `dropped` with the owner's decision), and for `done` the test that proves it. **A source directory may be deleted only when every one of its capabilities is `done` or `dropped`** and its content has been imported. parodynews (barodybroject) is absorbed *in full* — every capability its inventory lists, including its posts, versions, assistants, groups, schemas and threads — and so is AIEO. | `tools/check_absorption.py`: a missing source with an open capability fails; a `done` row without an existing proof fails; a `dropped` row without `decided_by` fails; a row whose `target` is not a platform capability fails |
| 11 | **The image generator's Python engine is absorbed; its Ruby leaves.** The engine and the panel's features become the platform's `media` app; the Ruby port and the gem leave this repository. Whether the gem lives on in its original repository for outside Jekyll users is the owner's call (PLAN §7 P-D2). | ratchet ceiling for `packages/zer0-image-generator/` reaches 0 in G6 |
| 12 | **The workspace tool becomes Python.** `bin/zer0` keeps its commands and their output (`list`, `info`, `run`, `affected`, `matrix`, `routes`, `check`, `vendor`, `doctor`, `tags`) and its tests are ported; `zer0-workspace.yml`, `pages.yml` and `sites.yml` stop installing Ruby. | PLAN P3; the ported tests |

## What an agent must not do

Each of these has happened here, or is the next obvious mistake. Each is a review rule in `AGENTS.md`.

- Add Ruby anywhere, or build a feature on Rails, Jekyll, the image-generator gem or `bin/zer0` that a later milestone would have to port.
- Add screens to the Wagtail admin. New UI is React in `web/` — and its counterpart in the extension, or a recorded gap.
- Call a model provider's SDK outside the adapter registry, or add a second LLM client, ledger or registry.
- Port a merged app's models and views one to one. Map its capabilities onto the platform's model and import its data.
- Hand-roll what an established library does (an editor, a diff, auth, a job queue, a schema validator, a query cache) without a reason in the pull request.
- Edit, vendor or re-import the zer0-mistakes theme. Its home is `bamr87/zer0-mistakes`; `web/` ports its *design* at a recorded tag.
- Delete a source directory, a site, content or a capability because it looks obsolete, or mark a capability `dropped`. Deletion follows the ledger, and dropping is the owner's decision.
- Run a fleet-wide kit (docs framework, governance, standards) over an imported project as if it were a live product. The projects under `apps/`, `packages/`, `rails/` and `sites/` are **sources being absorbed**; fleet kits apply to the platform, `web/` and the extension.
- Pick work by "the first unchecked box". The order of work is PLAN § 3's list.
- Stack a pull request on another unmerged branch. Base every pull request on `main`.

## Consequences

- One language per role: Python on the server and in tooling, TypeScript in the browser and the editor. One deploy artifact for the backend, one build for the frontend, one API contract for both clients.
- The absorption is long, so it is observable: the ledger is the progress report, the ratchet's ceilings are the Ruby burn-down, the surface columns are the extension/studio parity report, and all three fail CI when they move the wrong way.
- Sites keep publishing from Jekyll until their renderer parity fixture is green, so no site goes dark. The price is ordering: each site's Jekyll build must be recorded *before* its Ruby is removed (P1 comes first for that reason).
- The studio must reach the Wagtail admin's coverage before editors lose the admin; until then both exist — a temporary second UI, accepted and bounded by P2's accept criteria.
- The platform now carries every absorbed product's complexity. Libraries carry most of it; the service-layer and async rules in decision 6 are what keep the rest manageable.

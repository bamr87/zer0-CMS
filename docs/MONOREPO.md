# The zer0 monorepo

zer0-CMS now carries the whole zer0 stack in one repository. The theme, the image generator and the four Jekyll sites that used to live in their own repositories were imported here **with their full history**, each under its own directory. This page explains the layout, how the import was done, and what still depends on the original repositories.

## Layout

| Path | Was | What it is |
|---|---|---|
| `src/`, `rails/`, `docs/`, … | `bamr87/zer0-CMS` | The VS Code extension and the Rails fleet CMS. Nothing here moved. |
| `packages/zer0-mistakes/` | `bamr87/zer0-mistakes` | The Jekyll theme, published as the `jekyll-theme-zer0` gem. |
| `packages/zer0-image-generator/` | `bamr87/zer0-image-generator` | The preview-image engine, published as the `zer0-image-generator` gem, plus its Rails web panel. |
| `sites/zer0-pages/` | `bamr87/zer0-pages` | The Obsidian-vault + Jekyll site. Its `claude-obsidian` submodule is declared in the root `.gitmodules`. |
| `sites/zer0-pages-remote/` | `bamr87/zer0-pages-remote` | The minimal `remote_theme` consumer demo. |
| `sites/zer0-demo-cookbook/` | `bamr87/zer0-demo-cookbook` | A demo site generated by the theme's installer. |
| `sites/zer0-demo-garden/` | `bamr87/zer0-demo-garden` | A demo site generated by the theme's installer. |

`packages/` holds what gets published as a library; `sites/` holds what gets published as a website. Each imported directory keeps its own `README.md`, `CLAUDE.md` and tooling, and each one's commands still run from inside that directory (`cd packages/zer0-mistakes && ./scripts/bin/test`).

## How the import was done

Every repository's `main` was rewritten with `git filter-repo --to-subdirectory-filter <path>` and merged with `--allow-unrelated-histories`, one merge commit per repository. So `git log -- packages/zer0-mistakes/_layouts/default.html` and `git blame` work as they did in the original repository; only the commit hashes changed. Bare issue references in the imported commit messages (`#123`) were rewritten to `bamr87/<repo>#123`, so they still point at the original repository's issues and pull requests rather than at unrelated zer0-CMS numbers. Tags were **not** imported: every repository has its own `v1.x.y` series and they would collide. The original tags and releases stay on the original repositories.

To import one more repository the same way:

```bash
git clone --single-branch --branch main https://github.com/bamr87/<repo> /tmp/<repo> && cd /tmp/<repo>
git tag -l | xargs -r git tag -d
git filter-repo --to-subdirectory-filter sites/<repo> \
  --message-callback "import re; return re.sub(rb'(?<![\w/.-])#(\d+)\b', rb'bamr87/<repo>#\1', message)"
cd - && git fetch /tmp/<repo> main:refs/import/<repo> && git merge --allow-unrelated-histories refs/import/<repo>
```

## What changed so the code runs from its new path

- **`docker-compose.yml`** builds the `imagegen` profile from `./packages/zer0-image-generator` by default instead of a sibling `../zer0-image-generator` checkout. `ZER0_IMAGE_GENERATOR_DIR` still overrides it.
- **`packages/zer0-mistakes/scripts/lib/common.sh`**: `get_repo_root` resolved the theme root with `git rev-parse --show-toplevel`, which is now the zer0-CMS root. It now resolves two levels above `scripts/lib/`, which is correct both here and in a standalone checkout.
- **The `claude-obsidian` submodule** moved from `sites/zer0-pages/.gitmodules` to the root `.gitmodules`, because git only reads `.gitmodules` at the repository root.
- **CI**: GitHub only runs workflows in the root `.github/workflows/`, so every imported `.github/workflows/` directory is inert here. Two gates were ported so far: `zer0-image-generator.yml` (the package's old `test.yml`) and `zer0-pages.yml` (the bridge/graph unit tests and the SCHEMA.md lint). Both are path-filtered to their own tree. `extension.yml` now ignores `packages/**` and `sites/**`, so a theme change does not download VS Code.

To browse the in-repo sites in the fleet CMS: `SITES_DIR=./sites docker compose up --build`.

## What still depends on the original repositories

Do **not** archive or delete the original repositories yet. Each one still does something this monorepo does not do yet:

| Original repository | Still does | What it takes to move it here |
|---|---|---|
| `bamr87/zer0-mistakes` | Its ~29 workflows, including the release-please → RubyGems release of `jekyll-theme-zer0`, the docs-site Pages deploy, visual evidence, translation and the issue autopilot. It is also the **`remote_theme: bamr87/zer0-mistakes` source** every GitHub Pages consumer names, and GitHub Pages can only load a remote theme from the root of a repository. | Port the workflows with `working-directory: packages/zer0-mistakes` and path filters, and turn release-please into a multi-package config. For `remote_theme`, either keep the original repository as a read-only mirror fed by `git subtree split --prefix packages/zer0-mistakes`, or move every consumer to the gem. |
| `bamr87/zer0-image-generator` | The release-please → RubyGems release of the gem. | Add the package to the root `release-please-config.json` as a second package. |
| `bamr87/zer0-pages` | The GitHub Pages deploy (`pages.yml`) to `bamr87.github.io/zer0-pages/`. | Port `pages.yml` with the site's working directory. The Pages URL of this repository would become `/zer0-CMS/` unless a custom domain is set. |
| `bamr87/zer0-pages-remote`, `zer0-demo-cookbook`, `zer0-demo-garden` | Native GitHub Pages builds from each repository's root. | One Pages site per repository is a GitHub limit, so these need an Actions deploy each (to one site under sub-paths) or a mirror. |
| `bamr87/bamr87` (the hub) | Registers each repository as its own submodule in `_data/projects.yml`. | Point the six entries at this repository and its sub-paths. |

Until those moves are done, a change made here does not reach the original repositories by itself. Pick one direction per repository and stick to it: either the monorepo becomes the place where work happens and the original is refreshed from it with `git subtree split --prefix <path> -b <branch> && git push <original> <branch>:main`, or the original stays authoritative and its new commits are re-imported. Doing both at once means the two copies drift apart.

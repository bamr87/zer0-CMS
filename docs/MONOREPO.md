# The zer0 monorepo

> Every project under `packages/`, `sites/` and `apps/` — the sources the platform is absorbing (ADR 0006) — how `workspace.yml` and `bin/zer0` manage them as one repository, how they were imported with their history, and what still runs from the originals.

zer0-CMS carries the zer0 stack's content-management half in one repository: the Django + Wagtail platform that is its centre ([ADR 0001](adr/0001-target-architecture.md), [ADR 0004](adr/0004-one-platform.md)), the VS Code extension that is its editor client, plus the image generator, the books app, nine Jekyll sites and the parodynews and aieo apps — the image generator's panel, the books studio and both apps being absorbed into the platform function by function (PLAN Phase G). The zer0-mistakes theme the sites build with is developed in its own repository, [bamr87/zer0-mistakes](https://github.com/bamr87/zer0-mistakes), together with its Rails studio ([ADR 0005](adr/0005-theme-goes-home.md)), and reaches the sites here only through the Jekyll-theme option ([ADR 0006](adr/0006-one-python-platform.md) decision 4, PLAN P2): a site's `render:` setting in `workspace.yml` pins the theme's tag and the Jekyll server that builds it in Docker (`tools/jekyll_theme.py`), with no Gemfile — every site but zer0-pages, which still builds with its own until its two recorded differences are accepted. Each of those used to live in its own repository and was imported here **with its full history**, under its own directory. This page explains how the pieces fit, how one repository manages all of them, how the import was done, and what still runs from the original repositories.

## How one repository manages all of them

The design has five parts. Each one replaces something that used to be repeated, by hand, in every repository.

```text
workspace.yml ──► bin/zer0 ──► list · info · run <task> · affected · check · vendor · doctor
     │                │
     │                ├─► root CI: one workflow per project, path-filtered to its tree
     │                │     + zer0-workspace.yml, the gate that keeps the manifest honest
     │                │
     │                └─► vendored: copies one project ships of another's file, checked byte-for-byte
     │
     └─► site: roots ──► the CMS's own `zer0 doctor` over every zer0 site in the repository
```

**1. One registry — `workspace.yml`.** Every project is an entry: its path, kind and toolchain, a one-line summary, where it came from, what it depends on inside the repository, what it publishes, the root workflow that gates it, the Jekyll root of a zer0 site, and its tasks — `setup`, `check` (the fast tier), `test` (the full suite) and `build`. A command is written once, here, in the same words a contributor would type in the project's directory.

**2. One command — `bin/zer0`.** It reads the registry and is Python with PyYAML alone (it was stdlib Ruby until PLAN P5, and keeps that tool's commands and output), so it runs before any project's own dependencies are installed. Where `python3` has no PyYAML and refuses a global `pip install` (Homebrew, Debian), `python3 -m venv .venv && .venv/bin/pip install pyyaml` once, and `bin/zer0` runs on that `.venv` by itself ([`tools/workspace/README.md`](../tools/workspace/README.md)):

```bash
bin/zer0 list                       # every project: path, kind, what it publishes, what gates it
bin/zer0 info drsai                 # one project: tasks, dependencies, dependents
bin/zer0 run check                  # the fast tier of every project, each in its own directory
bin/zer0 run test --affected        # the full suite of what this branch changed, plus its dependents
bin/zer0 affected --base origin/main
bin/zer0 check                      # the workspace contract (below)
bin/zer0 vendor [--write]           # vendored copies: status, or re-copy from source
bin/zer0 doctor [--strict]          # the CMS's zer0 doctor over every zer0 site
```

"Affected" follows the dependency graph: a change to `packages/zer0-image-generator/` affects the gem and the site that builds on it, and a change to a root workflow affects the projects it gates.

**3. One CI, split by project.** GitHub only runs workflows in the root `.github/workflows/`, so each project has a root workflow filtered to its own tree — `extension.yml`, `content.yml`, `zer0-image-generator.yml`, `books.yml`, `drsai.yml`, `zer0-pages.yml`, `sites.yml` (the sites with no workflow of their own, one matrix leg each, through the Jekyll-theme option), `irony-works.yml`, `parodynews.yml` and `aieo.yml`. A pull request pays only for what it touches. [`CICD.md`](CICD.md) says what each one runs. `zer0-workspace.yml` runs on every pull request: the tool's own tests, then `bin/zer0 check`, which fails when

- a directory under `packages/`, `sites/` or `apps/` is not registered;
- a project's path or claimed glob matches nothing;
- a project's workflow is missing or no longer filters on its path — or, for a site it builds with the Jekyll-theme option, on what the option reads besides the site (`workspace.yml`, the workspace tool, the option and its server);
- a project says `ci: none` without a reason;
- a vendored copy has drifted from its source.

It also writes the affected projects and a report-only `zer0 doctor` of every site to the job summary.

**4. Vendored copies are a checked contract.** Some files must exist twice. None does today: the Rails CMS's copies went with it ([ADR 0008](adr/0008-retire-the-rails-cms.md)), and the projects that call `tools/unwrap-prose.py` reach the root's one copy by a project-relative path. `workspace.yml` lists each copy under `vendored:` with its single source and the reason the copy exists. `bin/zer0 vendor --write` re-copies, and `bin/zer0 check` fails CI on drift. The import found a real case: the CMS's `zer0-tokens.css` was still kit `1.0.0` while the image generator had shipped `1.0.1` (`--maxw` 1180px → 1320px). It is re-vendored here.

**5. The CMS manages the repository's own sites.** Every project with a `site:` root is a zer0 site, and `bin/zer0 doctor` runs the platform's `zer0 doctor` (`content/sites/doctor.py`, Python since PLAN G4; it needs PyYAML and jsonschema and says so when they are missing) against each, and the studio's Sites area runs the same doctor as a site's job. Docker Compose now mounts this repository as `SITES_DIR` by default, so `docker compose up --build` shows the in-repo sites, two levels down (`/sites/sites/drsai`), with no setup. `SITES_DIR=~/github` still points it at a wider fleet. The sites build with the Jekyll-theme option, the theme pinned by tag, so a theme release reaches a site only when its `render:` setting moves to it, with its recording re-made and the reason said.

### Today's doctor baseline

`bin/zer0 doctor` is report-only. On 2026-10-22 (PLAN G4) every site reports no error: their warnings are a missing `zer0.json` and `preview_images:` block. The step can become `--strict` once that holds for a while.

## How the import was done

Every repository's `main` was rewritten with `git filter-repo --to-subdirectory-filter <path>` and merged with `--allow-unrelated-histories`, one merge commit per repository — on the import branches. The pull requests that carried them (#29, #36) were then **squash**-merged, so `main` today holds each imported tree as a single commit, and `git log` and `git blame` under an imported path stop there. The rewritten histories are intact in `refs/pull/29/head` and `refs/pull/36/head`; cutover milestone C0 (`plan/PLAN.md`) grafts them back by fast-forward, after which `git log -- sites/drsai/_config.yml` and `git blame` work as they did in the original repository, with only the commit hashes changed. **Merge an import with a merge commit or a fast-forward, never a squash.** Bare issue references in the imported commit messages (`#123`) were rewritten to `bamr87/<repo>#123`, so they still point at the original repository's issues and pull requests rather than at unrelated zer0-CMS numbers. Tags were **not** imported: every repository has its own `v1.x.y` series and they would collide. The original tags and releases stay on the original repositories.

To import one more repository the same way, then register it:

```bash
git clone --single-branch --branch main https://github.com/bamr87/<repo> /tmp/<repo> && cd /tmp/<repo>
git tag -l | xargs -r git tag -d
git filter-repo --to-subdirectory-filter sites/<repo> \
  --message-callback "import re; return re.sub(rb'(?<![\w/.-])#(\d+)\b', rb'bamr87/<repo>#\1', message)"
cd - && git fetch /tmp/<repo> main:refs/import/<repo> && git merge --allow-unrelated-histories refs/import/<repo>
# then: add the project to workspace.yml, give it a root workflow, and run bin/zer0 check
```

## What changed so the code runs from its new path

- **Nothing may assume it is the git root.** The first case was the theme's `get_repo_root` (`scripts/lib/common.sh`), which used `git rev-parse --show-toplevel` and was changed at import to resolve from the script's own location; the theme has since gone back to its own repository ([ADR 0005](adr/0005-theme-goes-home.md)), and the rule stands for every imported project.
- **`docker-compose.yml`** builds the `imagegen` profile from `./packages/zer0-image-generator` and mounts this repository as `SITES_DIR` by default.
- **drsai** builds with the Jekyll-theme option (the theme at the tag `workspace.yml` pins, GitHub Pages' own builder); its ABC book `it-alphabet` is the deleted Rails wizard's output ([`plan/rails-cms-spec.md`](plan/rails-cms-spec.md)). `tools/import_dodge_and_reena.py` still defaults to a sibling `../Dodge-and-Reena-Book` checkout, which was not imported; pass `--source`.
- **The `claude-obsidian` submodule** is declared in the root `.gitmodules`, because git reads it nowhere else.
- **The vsix** excludes `packages/**`, `sites/**` and `apps/**`; `extension.yml` ignores them too.
- **Names.** `apps/parodynews/` was imported as `bamr87/barodybroject` and de-branded by [ADR 0003](adr/0003-framework-rebuild.md): its Django project package is `config`, its workflow is `parodynews.yml`, and only the `upstream:` field and this page still say where it came from.
- **Nested workflows.** Imported `.github/workflows/` directories never run here. The ones the root workflows replace completely were removed (30 files across books, the image generator, drsai, zer0-pages, zer0-pages-remote, 1987, 2005, aieo, irony-works and wargames). The ones not ported yet stay as reference: parodynews's 6, the image generator's `release.yml`, drsai's `ci.yml` (for its PyPI publish job) and `pages.yml`, zer0-pages' `pages.yml`, aieo's `release.yml`, `aieo-content-reusable.yml` and `aieo-it-journey-pilot.yml` (with its inert `dependabot.yml`), irony-works' `publish.yml`, `alanis-gate.yml` and `germinate.yml`, and wargames' `jekyll-gh-pages.yml`.

## What still depends on the original repositories

The direction is decided ([ADR 0002](adr/0002-one-home-cutover.md)): this repository is the only place work happens on what it holds, and every original is archived once nothing below is left for it to do. The theme is the exception ([ADR 0005](adr/0005-theme-goes-home.md)): `bamr87/zer0-mistakes` is developed in its own repository again and is not in this table. The cutover milestones C1–C7 in [`plan/PLAN.md`](plan/PLAN.md) empty this table in order; do **not** archive an original while it still has a row. The decisions this table used to wait on are made in ADR 0002, amended by ADR 0005 for the theme: the sites publish under this repository's one Pages site, one sub-path each; releases carry component-prefixed tags here; and every original is archived except the theme, which stays its own repository. Until an original's row is gone, a change made here still does not reach it by itself — and a change merged there must be re-imported (C1), never re-applied by hand. One direction per repository: doing both is how two copies drift apart.

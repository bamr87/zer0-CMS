# The zer0 monorepo

zer0-CMS carries the whole zer0 stack in one repository: the VS Code extension and the Rails fleet CMS it started with, the Django + Wagtail content plane that is becoming its centre ([ADR 0001](adr/0001-target-architecture.md)), plus the theme, the image generator, the books app, nine Jekyll sites and the barodybroject Django app. Each of those used to live in its own repository and was imported here **with its full history**, under its own directory. This page explains how the pieces fit, how one repository manages all of them, how the import was done, and what still runs from the original repositories.

## How one repository manages all of them

The design has five parts. Each one replaces something that used to be repeated, by hand, in every repository.

```
workspace.yml ──► bin/zer0 ──► list · info · run <task> · affected · check · vendor · doctor
     │                │
     │                ├─► root CI: one workflow per project, path-filtered to its tree
     │                │     + zer0-workspace.yml, the gate that keeps the manifest honest
     │                │
     │                └─► vendored: copies one project ships of another's file, checked byte-for-byte
     │
     └─► site: roots ──► the CMS's own `zer0 doctor` over every zer0 site in the repository
```

**1. One registry — `workspace.yml`.** Every project is an entry: its path, kind and toolchain, a one-line summary, where it came from, what it depends on inside the repository, what it publishes, the root workflow that gates it, the Jekyll root of a zer0 site, and its tasks — `setup`, `check` (the fast tier), `test` (the full suite) and `build`. A command is written once, here, in the same words a contributor would type in the project's directory.

**2. One command — `bin/zer0`.** It reads the registry and is stdlib-only Ruby, so it runs in a bare checkout before anything is installed ([`tools/workspace/README.md`](../tools/workspace/README.md)):

```bash
bin/zer0 list                       # every project: path, kind, what it publishes, what gates it
bin/zer0 info drsai                 # one project: tasks, dependencies, dependents
bin/zer0 run check                  # the fast tier of every project, each in its own directory
bin/zer0 run test --affected        # the full suite of what this branch changed, plus its dependents
bin/zer0 affected --base origin/main
bin/zer0 check                      # the workspace contract (below)
bin/zer0 vendor [--write]           # vendored copies: status, or re-copy from source
bin/zer0 doctor [--strict]          # the CMS's zer0 doctor over every zer0 site
```

"Affected" follows the dependency graph: a change to `packages/zer0-mistakes/` affects the theme and every site that builds on it, and a change to a root workflow affects the projects it gates.

**3. One CI, split by project.** GitHub only runs workflows in the root `.github/workflows/`, so each project has a root workflow filtered to its own tree — `extension.yml`, `rails-app.yml`, `content.yml`, `zer0-mistakes.yml`, `zer0-image-generator.yml`, `books.yml`, `drsai.yml`, `zer0-pages.yml`, `sites.yml` (the `remote_theme` sites, one matrix leg each), `irony-works.yml` and `barodybroject.yml`. A pull request pays only for what it touches. [`CICD.md`](CICD.md) says what each one runs. `zer0-workspace.yml` runs on every pull request: the tool's own tests, then `bin/zer0 check`, which fails when
- a directory under `packages/`, `sites/` or `apps/` is not registered;
- a project's path or claimed glob matches nothing;
- a project's workflow is missing or no longer filters on its path;
- a project says `ci: none` without a reason;
- a vendored copy has drifted from its source.

It also writes the affected projects and a report-only `zer0 doctor` of every site to the job summary.

**4. Vendored copies are a checked contract.** Some files must exist twice. The Rails app is its own Docker build context, `rails/lib` loads no gem, and several projects call `tools/unwrap-prose.py` by a project-relative path. `workspace.yml` lists each copy under `vendored:` with its single source and the reason the copy exists. `bin/zer0 vendor --write` re-copies, and `bin/zer0 check` fails CI on drift. The import found a real case: the CMS's `zer0-tokens.css` was still kit `1.0.0` while the image generator had shipped `1.0.1` (`--maxw` 1180px → 1320px). It is re-vendored here.

**5. The CMS manages the repository's own sites.** Every project with a `site:` root is a zer0 site, and `bin/zer0 doctor` runs the CMS's `zer0 doctor` (`rails/bin/zer0-cms`, stdlib-only) against each. Docker Compose now mounts this repository as `SITES_DIR` by default, so `docker compose up --build` shows the in-repo sites, two levels down (`/sites/sites/drsai`), with no setup. `SITES_DIR=~/github` still points it at a wider fleet. drsai builds against `packages/zer0-mistakes` through its `ZER0_THEME_LOCAL` override, so a theme pull request that breaks drsai fails on the theme's own CI.

### Today's doctor baseline

`bin/zer0 doctor` is report-only because two sites carry errors that predate the merge, both visible in their original repositories:
- `packages/zer0-mistakes` keeps its in-repo ancestor engine (`scripts/lib/preview_generator.py`), which the doctor reports as a vendored preview fork until the theme retires it.
- `apps/barodybroject/src/pages` has one error of its own.

Make the step `--strict` once both are clean.

## How the import was done

Every repository's `main` was rewritten with `git filter-repo --to-subdirectory-filter <path>` and merged with `--allow-unrelated-histories`, one merge commit per repository — on the import branches. The pull requests that carried them (#29, #36) were then **squash**-merged, so `main` today holds each imported tree as a single commit, and `git log` and `git blame` under an imported path stop there. The rewritten histories are intact in `refs/pull/29/head` and `refs/pull/36/head`; cutover milestone C0 (`plan/PLAN.md`) grafts them back by fast-forward, after which `git log -- packages/zer0-mistakes/_layouts/default.html` and `git blame` work as they did in the original repository, with only the commit hashes changed. **Merge an import with a merge commit or a fast-forward, never a squash.** Bare issue references in the imported commit messages (`#123`) were rewritten to `bamr87/<repo>#123`, so they still point at the original repository's issues and pull requests rather than at unrelated zer0-CMS numbers. Tags were **not** imported: every repository has its own `v1.x.y` series and they would collide. The original tags and releases stay on the original repositories.

To import one more repository the same way, then register it:

```bash
git clone --single-branch --branch main https://github.com/bamr87/<repo> /tmp/<repo> && cd /tmp/<repo>
git tag -l | xargs -r git tag -d
git filter-repo --to-subdirectory-filter sites/<repo> \
  --message-callback "import re; return re.sub(rb'(?<![\w/.-])#(\d+)\b', rb'bamr87/<repo>#\1', message)"
cd - && git fetch /tmp/<repo> main:refs/import/<repo> && git merge --allow-unrelated-histories refs/import/<repo>
# then: add the project to workspace.yml, give it a root workflow, and run bin/zer0 check
```

## What changed so the code runs from its new path

- **Nothing may assume it is the git root.** The theme's `get_repo_root` (`scripts/lib/common.sh`) used `git rev-parse --show-toplevel`, which is now the zer0-CMS root. It now resolves from the script's own location, which is right here and in a standalone checkout. A gem built from `packages/zer0-mistakes/` packs exactly the 544 files a build from the original repository does.
- **`docker-compose.yml`** builds the `imagegen` profile from `./packages/zer0-image-generator` and mounts this repository as `SITES_DIR` by default.
- **drsai** builds against `../../packages/zer0-mistakes`, and the ABC wizard's `--out` is `../sites/drsai` from `rails/`. `tools/import_dodge_and_reena.py` still defaults to a sibling `../Dodge-and-Reena-Book` checkout, which was not imported; pass `--source`.
- **The `claude-obsidian` submodule** is declared in the root `.gitmodules`, because git reads it nowhere else.
- **The vsix** excludes `packages/**`, `sites/**` and `apps/**`; `extension.yml` ignores them too.
- **Nested workflows.** Imported `.github/workflows/` directories never run here. The ones the root workflows replace completely were removed (27 files across books, the image generator, drsai, zer0-pages, zer0-pages-remote, 1987, 2005, irony-works and wargames). The ones not ported yet stay as reference: the theme's 29, barodybroject's 6, the image generator's `release.yml`, drsai's `ci.yml` (for its PyPI publish job) and `pages.yml`, zer0-pages' `pages.yml`, irony-works' `publish.yml`, `alanis-gate.yml` and `germinate.yml`, and wargames' `jekyll-gh-pages.yml`.

## What still depends on the original repositories

The direction is decided ([ADR 0002](adr/0002-one-home-cutover.md)): this repository is the only place work happens, every original is archived once nothing below is left for it to do, and `bamr87/zer0-mistakes` stays as a read-only mirror because `remote_theme` can only load from a repository root. The cutover milestones C1–C7 in [`plan/PLAN.md`](plan/PLAN.md) empty this table in order; do **not** archive an original while it still has a row. Each one still does something this monorepo does not:

| Original repository | Still does | What it takes to move it here |

The three decisions this table used to wait on are made in ADR 0002: the sites move under one domain (`zer0-mistakes.com`, one sub-path each), releases carry component-prefixed tags here (the theme's is mirrored as a plain `v*` tag), and every original is archived except the theme's mirror. Until an original's row is gone, a change made here still does not reach it by itself — and a change merged there must be re-imported (C1), never re-applied by hand. One direction per repository: doing both is how two copies drift apart.
